## 2024-08-04 - [Struct Serialization Leaks]
**Leak Pattern:** Sensitive structs containing raw cryptographic material (`key.WrappedKey`, `application.WrappedKeyInput`, `session.RefreshToken`, `crypto.SecretManager`) were defined without custom `String()` methods. If these structs were passed to default formatters (like `%+v` in `fmt.Printf` or `slog.Any`), their unexported sensitive fields (`wrappedDEK`, `tokenHash`, `secretKey`) would be silently serialized to logs.
**Learning:** The codebase currently lacks a systemic logging framework wrapper that would automatically detect and redact structs with sensitive material based on tags or other markers. As a result, every call site formatting a struct is a potential leak vector.
**Prevention:** Implement a `String()` method on any struct that holds a secret value (e.g. `WrappedKey`, `WrappedKeyInput`, `RefreshToken`, `SecretManager`). The `String()` method must explicitly omit or redact the sensitive fields (`***REDACTED***`). This serves as a fail-safe, ensuring the secret won't be exposed even if a developer inadvertently uses a default format string in the future.
## 2024-08-06 - [Application Flow Structs Leakage]
**Leak Pattern:** Data structures handling inputs and outputs for sensitive application layer flows (e.g. `LoginInput`, `LoginOutput`, `FinishInviteRegistrationInput`, `FinishInviteRegistrationOutput`) were holding unredacted fields like `ChallengeToken`, `AccessToken`, and `RefreshToken`. Any generic logger that receives these input/output structs would unknowingly log the tokens.
**Learning:** Security at the domain layer (`key.WrappedKey`, `session.RefreshToken`) and infrastructure layer (`crypto.SecretManager`) is insufficient. Security and redaction mechanisms must be applied to all boundaries, specifically to application-layer structures that transfer these sensitive fields.
**Prevention:** Implement `String()` methods for all application use case DTOs that handle sensitive security tokens, redacting them consistently (`***REDACTED***`). Apply `// SECURITY: never log this field` comments to trace these fields.
## 2025-02-12 - Missing String() redaction for infrastructure crypto wrappers
**Leak Pattern:** Infrastructure wrapper structs holding third-party cryptographic keys (like `paseto.V4SymmetricKey` in `TokenCodec` and `paseto.V4AsymmetricSecretKey` in `AccessTokenIssuer`) did not implement a custom `String()` method, making them susceptible to leaking raw key material if logged via `%+v` or `%#v`.
**Learning:** While domain entities had `String()` redaction safeguards, infrastructure wrappers for third-party libraries were overlooked, creating a systemic gap for key material leakage.
**Prevention:** Always implement `String()` methods with redaction (and add `// SECURITY: never log this field`) on any struct that holds cryptographic key material, including infrastructure wrappers for external libraries.

## 2025-08-11 - [CRITICAL] Prevent WebAuthn SessionData Leakage via DTO Stringers
**Leak Pattern:** Intermediate challenge payload structs in `internal/infrastructure/auth/webauthn` (like `loginChallengePayload` and `challengePayload`) store `gowebauthn.SessionData`. This third-party struct contains sensitive challenge parameters and could leak raw contents if passed to logs. Since it originates from a 3rd-party library, we cannot control its `String()` method, making it susceptible to leaking if the wrapper structs do not explicitly redact it.
**Learning:** External dependencies' struct types (like `gowebauthn.SessionData`) shouldn't be trusted to omit sensitive fields when serialized, so any wrapper struct containing them must actively implement redaction via custom `String()` methods.
**Prevention:** DTOs and intermediate structs (like `loginChallengePayload`, `challengePayload`) must implement a `String()` method that uses `***REDACTED***` for any embedded 3rd-party structs holding cryptographic challenge/session parameters, accompanied by `// SECURITY: never log this field` comments.
## 2025-02-12 - Prevent Leakage of Cryptographic Constants in Config Dump
**Leak Pattern:** The configuration flattening and dumping utility `config.DumpFlat()` redacted some sensitive keywords (`secret`, `key`, `pass`, `token`), but missed critical cryptographic terms like `hmac`, `prf`, `seed`, `nonce`, and `metadata`. This oversight could lead to plaintext exposure of cryptographic parameters if the configuration is dumped to logs or standard output.
**Learning:** Hardcoded exclusion lists for sensitive keywords need continuous review and expansion. They are prone to missing domain-specific cryptographic terminology.
**Prevention:** Include a comprehensive set of cryptographic keywords (`hmac`, `prf`, `seed`, `nonce`, `metadata`) in redaction utilities by default to provide robust defense-in-depth against configuration leaks.
