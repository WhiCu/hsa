## 2024-08-06 - [Application Flow Structs Token Leakage]
**Vulnerability:** Found unredacted sensitive tokens (`ChallengeToken`, `AccessToken`, `RefreshToken`) within application layer DTOs like `LoginInput`, `LoginOutput`, `FinishInviteRegistrationInput`, and `FinishInviteRegistrationOutput`.
**Learning:** Security redaction was well-implemented at the domain and infrastructure levels (like `key.WrappedKey` and `crypto.SecretManager`), but there was a gap at the application layer where raw strings of these tokens were being packaged into struct inputs/outputs. Standard formatters (like `%+v` in `fmt.Printf` or structured loggers) would silently log these sensitive strings.
**Prevention:** Ensured that `String()` methods are applied not just to domain entities but also to application layer inputs/outputs (DTOs) which carry sensitive fields to guarantee that `***REDACTED***` is output when logged. Added `// SECURITY: never log this field` to these implementations.
## 2024-08-07 - [Application Flow Structs Leakage Part 2]
**Vulnerability:** Data structures handling inputs and outputs for sensitive application layer flows (e.g., `RegistrationResult` and `AuthenticationResult` in `internal/application/auth.go`) were missing custom `String()` methods, making them susceptible to inadvertently logging raw byte fields like `PublicKey` and `ExternalID` (credential ID).
**Learning:** We successfully implemented redactions for `LoginInput/Output` and `FinishInviteRegistrationInput/Output`, but missed inner DTO structures representing authentication bounds (`RegistrationResult`, `AuthenticationResult`). Since a generic logging framework might inadvertently serialize any interface to a string format, all DTOs bridging the application or infrastructure layer boundaries that hold secrets must explicitly implement `String()`.
**Prevention:** Ensure that every struct definition passing around raw keys, tokens, or credential identifiers explicitly provides a `fmt.Stringer` interface implementation with fields labeled `***REDACTED***` and marked with `// SECURITY: never log this field`.
## 2024-08-08 - [Domain Entities Secret Leakage]
**Vulnerability:** Found unredacted sensitive fields (`externalID`, `publicKey` in `Credential`, and `codeHash` in `Invite`) in domain entities. These entities were missing custom `String()` methods, making them susceptible to inadvertently logging raw sensitive data when formatted using `%+v` or passed to structured loggers.
**Learning:** While redaction was previously added to application layer DTOs, domain entities themselves can also be inadvertently logged (e.g. during errors or debugging). Any domain entity holding sensitive material (hashes, external identifiers, public/private keys) must enforce its own redaction.
**Prevention:** All domain entities that contain sensitive information must implement a custom `String()` method that explicitly redacts sensitive fields using `***REDACTED***` and is marked with `// SECURITY: never log this field`.
## 2025-08-11 - [CRITICAL] Prevent PASETO Secret Leaks via Stringer
**Vulnerability:** PASETO symmetric and asymmetric keys stored in struct wrappers (`TokenCodec`, `AccessTokenIssuer`, `AccessTokenVerifier`) could be leaked if instances are passed to loggers or string formatters.
**Learning:** In Go, struct arguments to loggers natively reflect internal state unless explicitly handled. Types holding cryptographic keys must implement an explicit, redacting `String()` method to prevent implicit leakage.
**Prevention:** Always ensure structs holding security-sensitive fields (like `aidanwoods.dev/go-paseto` keys) implement a `String()` method that redacts the key and includes a `// SECURITY: never log this field` comment to signal intent and block naive stringification.
## 2025-02-12 - [CRITICAL] Prevent Webauthn Session Data Leaks via Stringer
**Vulnerability:** The webauthn challenge session payloads (`challengePayload` and `loginChallengePayload` which embed `gowebauthn.SessionData`) did not have custom `String()` methods. `gowebauthn.SessionData` contains `Challenge` and `UserID` arrays. If these wrappers were inadvertently logged (e.g. using `%+v`), the underlying webauthn challenges would leak.
**Learning:** Structures handling authentication flows, even those bridging third-party webauthn structs in infrastructure adapters, must implement redaction to prevent accidental exposure via logging.
**Prevention:** Ensure that all infrastructure payloads handling Webauthn session data explicitly implement a `fmt.Stringer` interface implementation with sensitive fields labeled `***REDACTED***` and marked with `// SECURITY: never log this field`.
## 2026-08-17 - [CRITICAL] Prevent Config Structure Leakage
**Vulnerability:** The infrastructure `crypto.Config` (and `crypto.PASETOConfig`) contained sensitive keys such as `HMACSecret`, `SymmetricKey`, `SecretKey`, and `PublicKey`. These configurations could implicitly leak sensitive credentials in plaintext if inadvertently logged using struct formatters (like `%+v` or `slog.Any`), since they lacked a `String()` method.
**Learning:** Structures containing configuration values are just as vulnerable to log-leakage as application or domain entities. Any configuration struct holding cryptographic secrets must explicitly implement `String()`.
**Prevention:** Always implement a `String()` method with a `// SECURITY: never log this field` comment on configuration structs that contain keys, redacting those sensitive fields using `***REDACTED***`.
## 2026-08-23 - [CRITICAL] Prevent Config Dump Flat Leakage
**Vulnerability:** The `DumpFlat` function in `internal/config/koanf.go` iterated over nested maps via `k.All()` and formatted them without redaction checks, potentially exposing highly sensitive credentials (like passwords, tokens, HMAC secrets, etc.) in plaintext to logs or standard output when the configuration structure was dumped.
**Learning:** Utilities that dump raw configuration data dynamically (without struct tags) are major blind spots for credential leakage. Since they bypass struct-level `String()` redactions, they must include robust, programmatic redaction checks for common sensitive keywords before outputting values.
**Prevention:** Always implement explicit redaction checks when dumping configuration data natively via `koanf`. Use flattened keys (`k.Keys()`) instead of nested maps (`k.All()`) to accurately scan the full path of the key. Redact the printed value using `***REDACTED***` if the flattened key string contains keywords like `secret`, `key`, `pass`, or `token`.
